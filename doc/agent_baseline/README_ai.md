## 0. 一句话

在 LEVIR-CD 上做第一个**真正由 Agent 调度工具**的变化检测 baseline：Agent 拿到两期影像和一句自然语言指令，自己调用原子工具生成 building 变化掩码，自己决定要不要核实、补漏、修边界，最后提交。整个过程留下完整轨迹。

## 1. 背景：为什么要做这个（先读）

- 研究方向已经从「接在检测器后面优化掩码」转为「变化检测 Agent 接管整个工作流」。创新点：① Agent 接管 CD 工作流；② Agent 能优化掩码（一类任务）；③ 可能有一个 benchmark。
- 之前的 `code/ovcd_v0/`（11 轮，结果见 `results/ovcd_v0_baseline.md`）是**程序编排**：初始化方法写死（M-C-I / I-M-C / ReA-OVCD），A→B→C 顺序写死，MLLM 只回答 yes/no 和画框。设计文档 `doc/ovcd_agent_v0.md` 里的 M5「MLLM 自己选动作」一直没做。
- 本 baseline 和 ovcd_v0 的根本区别：**没有任何「一键出变化掩码」的工具**。M-C-I、I-M-C 被拆成原子工具，由 Agent 自己组合；A/B/C 变成 Agent 可以选择调用的修改工具。
- 任务体系（已定稿，见 `doc/cd_agent_task_design.html`）：本 baseline 对应 **T1.1 × C0**（给定类别，从零生成掩码）；掩码修正 / 已有结果更新是 **T5**，第一版做 **T5.1**（旧编号 F / F.1 已废弃）。**本 baseline 只做 LEVIR + building，但接口必须能接受自然语言指令，并能接受一个给定初始掩码**，以后不改框架就能扩到这些任务。

## 3. 任务定义

| 项 | 定义 |
|---|---|
| 输入 | `T1`、`T2`（LEVIR 1024×1024 RGB）+ 一句指令 `instruction` + 可选的初始掩码 `init_mask`（T1.1 不给；T5.1 给 SAM3 变化掩码） |
| 默认指令 | `"Find all buildings that changed between T1 and T2 (newly built or demolished). Output a binary change mask."` 另跑一个中文版做稳定性对照 |
| 输出 | 二值变化掩码 + 轨迹 |
| Agent 可见 | 系统提示、工具说明、building 口径卡（复用 `code/ovcd_v0/prompts.py` 的 `SCOPE_CARD`）、预算 |
| Agent 不可见 | 数据集名、真值、任何评测数字、「哪条路线最好」的提示 |
| 训练 | 不训练 |
| 真值 | LEVIR 二值标签，`code/ovcd_v0/common.py::load_gt` |

**关键约束：真值只在记录器里用来算每一步的 F1，绝不能出现在 Agent 的任何输入里。** 写一个单元测试检查规划器收到的消息里没有任何 F1/IoU/GT 字段。

## 4. 工具集

原则：
- 每个工具只做一件事。**禁止**提供 `run_mci()`、`run_imc()`、`run_reaovcd()` 这类组合工具，也不提供 SChanger 等在 LEVIR 上训练过的检测器（另一种设定再说）。
- 大对象（掩码、提议集、特征图）存在工具服务的**状态仓库**里，按句柄引用：`mask#3`、`props#1`、`feat#2`。工具只返回句柄 + 简短统计（个数、面积、分数分布）。
- 只有 `view` 返回图像。
- 每个工具有 OpenAI function calling 格式的 JSON schema（名字、描述、参数）。工具描述就是 Agent 能看到的全部说明，写清楚输入输出和适用场景，**不写**「哪个组合效果最好」。
- 工具就是普通 Python 函数，带 schema；JSON 循环和 CodeAgent 共用同一份实现。以后发 benchmark 时再套 MCP 外壳，工具本身不改。

| 类别 | 工具 | 参数 | 返回 | 底层实现（已有） |
|---|---|---|---|---|
| 看 | ★ `view` | `region`（可选 xyxy，默认全图）、`overlay`（可选 mask 句柄）、`label_components`（bool） | T1、T2 两张图（放大到 768² 以内），可叠加红色轮廓和连通域编号 | `code/ovcd_v0/render.py` |
| 看 | ★ `inspect` | `mask` | 连通域清单：编号、面积、外接框，若有来源分数一并给出；最多列 50 个，按面积降序 | `common.components` |
| 分割 | `segment_everything` | `time`（t1/t2） | `props#k`：无类别 SAM 提议集，个数和面积分布 | SAM ViT-H；第一版直接读 M-C-I 导出缓存（`common.MCI`，`queues.read_dump`），每图约 600 个 |
| 分割 | ★ `segment_text` | `time`、`text`、`tile`（0 或 512）、`score_thr`（默认 0.5） | `inst#k`：实例集，个数、分数 | SAM3（`code/ovcd_v0/sam3_t7.py`，已有 text="building" 的缓存；其他文本要现算） |
| 分割 | ★ `segment_prompt` | `time`、`box` 或 `point` | `mask#k`：一个目标 | SAM ViT-H 提示模式，`code/ovcd_v0/sam_tools.py`（嵌入缓存 + CPU 解码） |
| 特征 | `extract_features` | `time`、`model`（dinov2） | `feat#k` | DINOv2；同上，第一版可读 M-C-I 缓存 |
| 比较 | `compare_features` | `feat_t1`、`feat_t2`、`props` | 给提议集每个提议附上两期特征差异分数（−cos），返回分布 | M-C-I 的 C 步，缓存里已有 |
| 比较 | ★ `match_instances` | `inst_t1`、`inst_t2`、`iou_thr`（默认 0.25） | `appeared#k`、`disappeared#k`、`unchanged#k` 三个实例集 | OmniOVCD overlap_presence |
| 语义 | `classify` | `props`、`time`、`text` | 给每个提议附上该时相属于 `text` 的概率 | SegEarth-OV，M-C-I 的 I 步，缓存里已有 building 两期概率 |
| 语义 | ★ `ask` | `regions`（掩码句柄 + 连通域编号列表，**支持批量**）、`question` | 每个区域的 P(yes)、类型、一句理由 | Qwen3.5-4B 本地 + `code/ovcd_v0/mllm.py` 的 yes/no 读数 |
| 运算 | ★ `select` | `set`、`where`（如 `score>0.57 and p_t1<0.5`）、`area`（min/max） | 子集句柄 | numpy |
| 运算 | ★ `to_mask` | `set` | `mask#k`（并集） | numpy |
| 运算 | ★ `combine` | `op`（union/intersect/subtract）、`a`、`b` | `mask#k` | numpy |
| 运算 | ★ `morph` | `mask`、`op`（open/close/fill_holes）、`radius` | `mask#k` | scipy |
| 修改 | ★ `remove_region` | `mask`、`ids` | `mask#k` | — |
| 修改 | ★ `add_region` | `mask`、`other`（掩码或实例句柄 + 编号） | `mask#k` | — |
| 修改 | ★ `refine_region` | `mask`、`id`、`prompt`（box/point，可选） | `mask#k`：该连通域用 SAM 重分割后替换 | v0 的 T6 |
| 结束 | ★ `submit` | `mask`、`summary`（文字说明） | — | — |

用这套工具：
- **M-C-I 路线** = `segment_everything(t1/t2)` → `extract_features` ×2 → `compare_features` → `classify` ×2 → `select` → `to_mask`。
- **I-M-C 路线** = `segment_text(t1,"building")`、`segment_text(t2,"building")` → `match_instances` → `combine(union, appeared, disappeared)`。
  注意：DynamicEarth 原版 I-M-C 用 APE 做识别（测试 69.67），这里用 SAM3，数字会不同；要单独报。
- 用固定脚本把这两条路线拼出来，就是本 baseline 的「无 Agent」下界，也顺便验证工具拆分没有引入偏差：M-C-I 路线必须复现测试集 53.76（差 0.2 以内）。

可以按需要增删工具，但每次增删要写进第 11 节的变更记录，并说明理由。

## 5. 两种 Agent 形态（都做，同一套工具）

| 形态 | 每一步模型输出 | 实现 |
|---|---|---|
| **JSON 循环**（主线候选 1） | 一个或多个并行的 function call | 自己写，约 300 行 ReAct，`code/agent_baseline/loop_json.py`；OpenAI 兼容接口，本地 vLLM 和百炼共用 |
| **CodeAgent**（主线候选 2） | 一段 Python，里面调用工具函数 | smolagents `CodeAgent`，`code/agent_baseline/loop_code.py`；工具包装成 smolagents tool；代码执行用它的本地沙箱，限制 import |

哪种当主线，看验证集上的 F1、步数、失败率再定，写进第 11 节。

**CodeAgent 要额外记录**：模型写出的代码原文；代码里每一次工具调用（在工具包装层记录，和 JSON 循环同一格式），这样两种形态的轨迹可以用同一个回放页显示。另外统计「写死脚本」比例：一段代码里对所有区域按阈值批量删改、之后不再调用 `view`/`ask` 的图有多少。

## 7. 轨迹格式（服务器上的完整轨迹）

目录：`$AGENT_RUN/<config>/<split>/<image_stem>/`，`$AGENT_RUN` 默认 `/guisongxia01/pangchao/wangyihan/wyh/exp6_staging/agent_baseline_run`。`<config>` 例如 `json_qwen37plus_v1`。

```
<image_stem>/
  input.json          # 两期图路径、instruction、init_mask（无则 null）、系统提示全文的 sha1 与路径
  messages.jsonl      # 规划器每一次请求的完整消息（含图像路径引用）和完整原始回复，逐条追加；能逐字复现对话
  steps.jsonl         # 每一步一行，见下
  images/             # view 返回的图、每一步的掩码叠加图（PNG）
  masks/              # 每个 mask 句柄的 PNG（mask_<k>.png）
  final.json          # 任务编号（T1.1xC0 / T5.1）、最终掩码路径、summary 文字、变化目标个数与面积、submitted_by、本图 F1/IoU/P/R、步数、token、耗时
```

`steps.jsonl` 每一行：

```json
{
  "step": 3,
  "planner": {"request_id": "...", "input_tokens": 5123, "output_tokens": 212, "seconds": 2.1,
               "thought": "模型的推理文字（如果有）", "raw": "原始回复全文",
               "code": "CodeAgent 写的代码（JSON 循环为 null）"},
  "calls": [
    {"tool": "segment_text", "args": {"time": "t2", "text": "building", "tile": 512},
     "ok": true, "error": null, "seconds": 0.8,
     "result_text": "inst#2: 41 instances, score median 0.71",
     "result_images": [], "handles_created": ["inst#2"]}
  ],
  "current_mask": "mask#4",
  "eval": {"f1": 0.62, "iou": 0.45, "delta_f1": 0.07}
}
```

- `eval` 只由记录器写，用来画「每一步 F1 怎么变」，**绝不回传给规划器**。
- `current_mask` 定义：最近一次被 `submit` 之外的修改/生成工具产出的整图掩码句柄（由记录器按规则判断，规则写进代码注释）。
- 汇总：`$AGENT_RUN/<config>/<split>/summary.json`（整集 F1^c、IoU^c、P、R 用 `common.evaluate` 累计；整目标漏检率、误检率；逐图平均 F1；平均步数、token、耗时、费用；失败率；路线分类统计）。
- 路线分类（每张图一个标签，规则写死在代码里）：`mci_like`（用了 segment_everything + compare_features）、`imc_like`（用了两次 segment_text + match_instances）、`mixed`（两者都用）、`other`。另记「是否调用过修改类工具」和修改带来的 ΔF1。

### 每一轮的步骤

1. **诊断**：在验证集轨迹上做错误归因，每张错得多的图标一个主因：工具本身输出差、选错工具、参数不对、没看图就提交、停得太早或太晚、修改把对的删了、超预算。统计各主因的图数和 F1 损失。
2. **选改动**：优先改 F1 损失最大的主因，必须写明依据（哪几类错误、哪些图）。改动可大可小，见下面的「自主权」；小改动（门限、提示措辞）尽量一轮一个，便于归因；大改动（换工具、换架构）可以单独占一轮。
3. **验证**：重跑验证集（工具层改动先看单项指标，再看系统层）。变好就保留；没变好或变差就回滚，回滚也照样记录。
4. **Codex**：每两轮把诊断和改动方案给 Codex 看一次，意见写进记录。

### 规则

- 只看验证集。测试集只在外循环结束、配置冻结后评一次。
- BF 期间最多 2 轮，保证两天内出结果。BF 之后**不设轮数上限**，持续迭代；但连续 3 轮只调门限、超参，验证集提升都小于 0.3 时，下一轮必须尝试一个结构性改动（换工具、加工具、换 Agent 形态或换方向），不许在小参数上打转。
- 禁止把真值信息、数据集名或「LEVIR 的建筑长什么样」的专门规则写进提示，否则就是在验证集上过拟合。提示里只能写通用的方法性指导。
- 每轮的完整轨迹单独存一份（`<config>` 名里带轮次，如 `json_qwen37plus_r3`），方便对比回放。
- 说明：这是工程调优，相当于把人工调提示交给 Claude 来做，**不作为论文的方法贡献**；论文里要如实写「系统提示和工具说明在验证集上经过 N 轮迭代」。

### 复用而不是自造（Ethan 2026-11-04 问到）

- 缓存用百炼服务端 prompt 缓存，工具调用用 API 原生 function calling，这两样不自己实现，只保证消息前缀稳定。

## 10.5 优化方向 v2：规划器和验证器解耦（Ethan 2026-11-04 13:05 提出，Claude 整理；Ethan 13:12 要了开跑提示词，视为审核通过）

本节取代第 2.0 节旧的第 2、4 步，以及第 10.4 节 Gemini 修改里的 A、B 两条（理由见下）。第 10.4 节的 skill 写法规则和 C 条（`python` 默认关闭）继续有效。

### Ethan 的意见

1. skill 由 Claude 决定。T1.1 等于固定路线不是坏事，能超过就尽量超过。在能发挥 Agent 能力的地方充分发挥，动态调用工具链，做扎实。
2. 现在由规划器自己决定是否调用验证器。改成规划器 + 验证器解耦的结构（工作名「Agentic Self-Verification」）。验证器先试不训练的方法，比如给样本示例；示例也许可以做成规划器的工具。讲故事时不训练 MLP。确有必要训练，服务器上有 Qwen 视觉模型。
3. 转来的 Gemini 建议：`ask` 允许 `ids=None`，默认核验当前掩码里所有未核验的组件（超过 64 个时按面积取前 64 个）；MLLM 验证器有零样本和可解释（伪变化类型 + 理由）的优点。

### Claude 的判断

- **采纳 `ids=None`，并且更进一步：验证器成为固定阶段**，不再由规划器决定要不要核验。删不删仍由规划器决定。这覆盖第 4 次 Codex 讨论定的界线（「不能写成全部核验、答否就删」）：核验全部组件现在是结构，不是 skill 里的规程；「答否就删」仍然不写死。
- **「立刻追平 86.35」只在一种情况下成立**：T5.1 从给定掩码出发，规划器把所有答否的组件都删掉。那时 Agent 就是规则本身，Agent 的贡献是零。所以解耦以后，**规则 86.35 是 Agent 的下限，主结果要报告 Agent 相对规则的增量**：规划器在哪些组件上做了和规则不同的决定，这些决定净赚多少。
- **不训练 MLP。** 理由同 Gemini：任务体系的卖点是零样本、能换类别。服务器上的 Qwen 视觉模型微调只在 B 部分的不训练方法全部无效时，作为旁支消融，不进主结果。
- **示例放进验证器，不先做成规划器的看图工具。** 规划器拿到的选择是「核验强度」：对哪些组件多花核验成本。这既是规则做不到的，也不会让规划器去重新判读像素。规划器自己看示例的工具放到后面，作为一个消融。
- 「Agentic Self-Verification」「Decoupled Visual Verification」是 Gemini 给的说法。顶会是否普遍用这个名字，这里没有核对文献，写论文前再查。
- 核验这条路的空间有限：旧候选池上理想删除是 87.86；抽样里约一半被接受的纯误检在人眼看是真实变化，只是真值没标。所以要先离线算 0.85 候选池上的理想删除上限，再决定在验证器上投入多少。

### A. 架构：验证器成为固定阶段

| 部件 | 现在（r7） | 改成 |
|---|---|---|
| 何时核验 | 规划器自己决定是否调 `ask`；提交前复核只列清单 | 每次准备提交时，验证器**自动**核验当前掩码里所有未核验的组件，包括新加的。规划器也可以随时调 `ask()`，`ids` 默认为全部未核验组件，超过 64 个按面积取前 64 个 |
| 谁决定删除 | 规划器 | 仍是规划器。它看到全部判定后，对每个组件选择保留、删除、升级核验或精修，并在 summary 里写理由。**不加自动删除**；自动删除等于「否决型验证器」，单独作为一个消融 |
| 核验强度 | 一档 | L1 快速：现在的 flash 四图对应问法。L2 仔细：B 部分选出的示例 + 投票。L2 由规划器对有疑问的组件调用 |
| 新增的组件 | 未经核验也能留下 | 同样进入验证阶段。因此 Gemini A 条（非对称证据）不再单独实现，只保留「T5.1 不给新增类工具」这个消融 |
| 轨迹记录 | 只有 `ask` 的回答 | 每个组件记录：判定、`p_yes`、核验强度、规划器最终决定、是否与规则不同 |

### B. 验证器：不训练，先离线比较，再上线

在固定候选池上用 `ask_eval` 离线比较，不经过 Agent 循环，只花 flash 的钱。**选型在训练开发集 dev2 上做，验证集只报告一次**，避免第 10.3 节说的选择偏差。

| 变体 | 做法 | 针对的错误 |
|---|---|---|
| V1 示例 | 从训练集挑 6–8 对带标准答案的示例。答「否」的：同一栋楼的颜色、阴影、遮挡、视角不同。答「是」的：新建、拆除、工地。示例作为固定前缀，可以命中缓存 | 同一栋楼外观变化被判成新建（抽样约 44%） |
| V2 投票 | 近景、大范围、对齐裁剪各问一次，或同一问法采样 3 次，取多数或平均 `p_yes` | 单次回答不稳 |
| V3 模型分歧 | flash 和 plus 都问，两者不一致的组件交给 L2 | 难例 |
| V4 置信读数 | 修 flash 只有约 45% 的请求返回可用 `p_yes` 的问题：让回复的第一个词元就是答案，或者对需要置信的组件用 plus。门限在 dev2 上定 | 规划器决定是否升级时需要可靠的不确定度 |

保留标准：在 dev2 上，按答否删除的规则 F1 和 AUC 都高于 L1，按图配对 bootstrap 区间在零以上。之后才在验证集上跑一次。开思考已经试过（AUC 0.70，单价约 4 倍），不再试。

### C. 规划器发挥的地方（规则做不到的部分）

1. **升级核验**：面积大、`p_yes` 在中间段、或答否但删错代价大的组件，先用 L2 再核验，再决定。规则在 0.85 候选池上删掉了 39,344 个真变化像素，这是规划器能救回来的部分。
2. **放大补漏**：密集小住宅区 SAM3 几乎检不出（ovcd_v0 test_45）。规划器发现后，对这个区域放大重新分割（`segment_text` 加区域和放大倍数参数），新组件照样经过验证阶段。LEVIR 分析（`results/agent_baseline/levir_analysis.md`）里的「理想添加」只用了现有实例，不能说明放大重分割没用，要单独测。
3. **边界**：单个组件外溢时，规划器用 SAM3 软输出换局部门限，或用 `morph` 局部修。先离线确认能赚，再开放给规划器。
4. **T1.1**：以固定路线作为默认起点（写进 skill），再做 1–3。等于固定路线是下限，不是问题。

- `rebuilt` 答案（在线账本，3 次合计，含重复核验）：T1.1 新建 63，拆除 110，C0 305；T5.1 新建 103，拆除 339。离线规则（去重区域）：新建 20，拆除 36。
- 兜底会话（3 次合计）：T1.1 新建 12，拆除 15，C0 25；T5.1 新建 6，拆除 5。错误会话 0。
- 费用：T1.1 × C1 39.8 元，T5.1 × C1 32.0 元，C0 25.3 元，合计 97.1 元。另有 CPU 版 C0 作废 3.9 元（`void/second_c0_cpu`，74 个会话）。

**怎么读：**
1. **T1.1 × C1 是 Agent 优势最清楚的地方。** 两个方向都比带方向的固定路线和规则高，区间都在零以上。LEVIR 上 Agent 和规则没有确认差异，这里方向约束拉开了差距：规则只能删固定路线的组件，召回被固定路线封顶（新建 51.54，拆除 28.50）；Agent 能自己找补，召回 64.04、39.99。
2. **T5.1 × C1 和规则持平。** 新建 +1.94，拆除 −0.43，区间都跨零。Agent 比给定掩码原样高很多，但主要是删反方向和误检。召回低于固定路线（53.96 对 57.38，28.47 对 36.09），没有补回漏检。
3. **同一方向，T5.1 比 T1.1 低**（新建 65.67 对 72.30，拆除 37.52 对 50.29）。给定掩码带着另一方向的组件，Agent 起点更乱，又倾向于在它上面删而不重新找。这和 LEVIR 不同：LEVIR 上 T5.1 稍高。
4. **方向违反率都很低**，只有 T5.1 拆除是 0.0449（第 1 次 0.0952）。反方向像素推测来自给定掩码里没删干净的新建组件，未逐张核对。
5. **拆除方向波动大**：T1.1 三次 45.86–55.22。拆除真值只有 838,368 像素，96 张图，少数大组件决定分数。
6. **C0 参照**：64.24，比 LEVIR 的 T1.1（val 约 84–85）低得多。SECOND 的建筑标注只在地类变化处，口径和 LEVIR 不同，两个数据集的分数不能直接比较。

**效率。** T1.1 × C1 和 T5.1 × C1 分别跑了 2 小时 59 分和 2 小时 24 分。原因：SECOND 的图没有预先算好的 SAM 编码，`segment_prompt` 每次在 CPU 上编码整张图，单线程约 150 秒（LEVIR 用预存编码，约 5 秒）；作业的 GPU 基本空闲。`code_m` 改为有 GPU 时用 GPU，一次调用 0.4–0.8 秒，每个进程约 6 GB 显存，3 个进程共用 1 张卡。C0 改用 `code_m` 后 46 分钟跑完 384 个会话。以后全量之前，先从试跑轨迹看每个工具的耗时。

### 口径：原址重建

- SECOND 只在两期地类不同时标变化，建筑换成建筑不算。LEVIR 把它算作变化，现有验证器也会答 yes。
- Agent 可以认出重建，只是按任务口径不交。验证器遇到这种情况答 no、类型 `rebuilt`，信息保留在轨迹里，以后 T3.3、T4.1 的「原址重建」任务可直接用。
- 口径必须告诉 Agent，不能让它猜：「新建的建筑」对普通用户有歧义。放进 SECOND 的范围卡（会话属性）：「同一位置的建筑被另一栋建筑取代，不算新建也不算拆除。」指令本身不变。
- 分析时统计 Agent 标出的 `rebuilt` 数量，作为它理解口径的证据。

### 11.3 费用与配额教训（2026-11-03）

- 单遍 64 对 × 2 任务：修复缓存前约 24 元，修复后约 20 元。
- **更正：之前写的「配额用尽」很可能不准确。** 错误类型是 `insufficient_quota`，但 144 路并发（约 350–470 万 token/分钟）才触发，报错后约 3.5 分钟就恢复；36 路（约 170 万 token/分钟）连续跑约 1 小时没有再触发。推断是单位时间限额，官方文档未核实。默认总并发不超过 36 路。
- 留图原来每轮原地改历史，丢图后那一轮命中率只有 47%。已改成累积到 7 对视图时才一次丢到 3 对，总命中率从 71% 升到 82–85%。第 6 节「最多 8 张图」因此变为最多 16 张。
- 已实现：配额错误让所有并行作业停止（`$AGENT_RUN/STOP.json`），被中止的会话不写 `final.json`，之后可续跑；`--batch`、`--max-cost-cny` 设费用上限；会话数不足时 `summarize.py` 拒绝汇总。
- 监控要看会话错误和停止开关，不能只看 Slurm 状态。
- 不用其他密钥或通道绕过配额。
- **2026-11-03 又作废一批（r3a、r3b 第一次）。** 预算账本是一个共享文件，多节点写入后出现 NUL 字节，记账抛异常，会话直接结束（717 个错误会话，3 分钟内由监控发现并取消，约 5.3 元）。原因是推断的：共享文件系统上跨节点追加不可靠。已改成每个进程只写自己的文件，总额按文件求和；账本写不进去时停止整批（可续跑），读不到别的进程时用它上次的值。修复后账本与消息日志的 token 费用核对一致。

### 11.2 与前文的偏差（已决定）

- `json_qwen37plus_r3ask_s*` 的 `input.json` 把 `ask_model` 写成了 qwen3-vl-plus，这是元数据错误。实际用的是 qwen3.7-plus，步骤记录里的后端信息是对的。之后的运行已修正。
- 配置 `json_qwen37plus_r3a_s*`、`json_qwen37plus_r3b_s*` 作废（`INVALID.txt`），有效的是 `r3idfix`、`r3ask`。

- 第 7 节 `input.json` 的 sha1 改为 `system_prompt_version` + 路径 + 全文。理由：工作区规范禁止在产物里写哈希。
- 第 7 节轨迹路径多一层任务名。
- `images/` 存发送给模型的 JPEG（q92），不是 PNG。理由：一次请求最多 8 张，PNG 请求体过大；存的就是实际发送的字节。
- `view` 画布是 768 再加 28 px 坐标边框。
- `match_instances` 参数名是 `overlap_thr`，返回 `appeared`、`disappeared`、`present_t2`。
- `ask` 去掉 `question` 参数，`segment_prompt` 用 `points`/`point_labels`，`inspect` 增加分页，`select` 增加 `ids`，`to_mask` 改为 `sets` 列表，修改类工具增加 `set_current`。
- 每轮最多执行 8 个工具调用；`ask` 单次最多 16 个区域。
- **SAM3 缓存口径**：工具和固定路线统一读 `sam3_t512_c0.1` 再按分数过滤。c0.1 过滤到 0.5 与直接跑 0.5 并不完全相同（验证集 10/64 张 T1 实例数不同），所以固定一个口径。
