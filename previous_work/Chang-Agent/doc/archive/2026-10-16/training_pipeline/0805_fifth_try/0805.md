## 问题一：普通推理路径几乎无法选择 SAM3 box

### 已确认的实现事实

这里的“production”特指近几轮正式冻结所用的 `qwen_staged + proposal` 路径，不泛指 runner 中仍保留的
direct/legacy verifier 模式。

1. 所有样本 reset 时都会先用 fresh SAM3 text prompt 生成 T1/T2 初始 building masks。受限的是后续迭代编辑，
   不是 SAM3 初始化。
2. `change_agent/verifier_regions.py:36-56` 只有在初始 T1/T2 masks 同时为空且启用扫描网格时，才生成
   `audit_kind=scan`。
3. `change_agent/adapters/staged_verifier.py:1284-1329` 将动作固定映射为：
   - `scan + false_negative → box → SAM3`；
   - 普通 `false_positive_change → negative_point → SimpleClick`；
   - 普通 `false_negative → positive_point → SimpleClick`；
   - `mixed_error/uncertain_region → staged _plan()` 本身不映射动作，详见问题四。
4. 这不是 Parser、Environment 或 Executor 的能力限制：
   - `change_agent/action_parser.py:17-78` 普遍接受 `box`；
   - `change_agent/environment.py:717-750` 能校验普通 live proposal 的精确 box；
   - `change_agent/executor.py:247-265` 会将 box 交给 SAM3，并在 ROI 内替换 mask；
   - `change_agent/verifier_protocol.py:177-202` 甚至把 box 列入普通 EvidenceRecord 的 `allowed_actions`；
   - 但 staged `_plan()` 没有使用这份 `allowed_actions`。

因此当前 staged production 并没有真正回答“该用 SAM3 还是 SimpleClick”；工具类型已经由程序按
`scan/error_type` 硬编码。0804 teacher-only 则会在普通 region 上实际执行多种 point/box 后用离线 GT 选最佳，
两条路径存在明确的 action reachability 与 teacher/deployment gap。

### 需要回答的问题

1. 对同一 `region + error_type + target_view`，哪些工具动作应成为合法候选？
2. 如何在不读取 GT、又不让模型任意创造 geometry 的前提下，从 SAM3 box 与 SimpleClick point 中选择一个？
3. 选择目标应是单步净改善、到 endpoint 的长期价值、语义安全，还是三者的组合？
4. box 会改变更大区域，可能收益更高，也可能更容易触发 semantic/hard gate；如何同时报告收益、风险和成本？
5. 如何避免因为 0804 的三个样本就把策略写死成“SAM3 优先”？

### 候选设计方向（尚未冻结）

建议把“语义诊断”和“工具选择”拆开：

1. Qwen/Verifier 只确定 `region、error_type、target_view`，Environment 继续拥有坐标与 box。
2. Environment 对普通 actionable region 枚举受约束的候选，例如：
   - SAM3 box；
   - SimpleClick positive/negative point（由 live seed polarity 决定）；
   - 每一步仍只提交一个最终动作。
3. 离线数据构造可真实执行成对候选，用 GT 计算 outcome、benefit 和 selection regret；GT 只作为标签，不能进入
   线上 selector 输入。
4. 线上候选选择至少有两类待比较方案：
   - **GT-free router/ranker**：用 RGB、当前 masks、component area/shape、诊断类型、模型置信度、历史动作与
     rejection history 预测工具收益和风险，再只执行 top-1；
   - **小型 shadow comparison**：对极少数 top-k 候选分别执行真实工具，再由 GT-free Verifier 比较候选结果；
     证据更直接，但工具调用与延迟更高。
5. 初始启发式可以把“完整对象缺失/大连通区域”偏向 box，把“小范围边界、孔洞、局部增删”偏向 point，
   但启发式只能作为 baseline，不能在配对实验前成为冻结规则。

### 动作路由验证门

新路由至少要报告：

- 同源 state/region/view 下 box 与 point 的候选覆盖率；
- 各工具的 beneficial/harmful/indeterminate、hard-gate 与 semantic-gate 通过率；
- GT-best tool、GT-free selector top-1 accuracy 与 improvement regret；
- endpoint reachability、平均工具调用数、墙钟与 GPU 成本；
- 按 train/val parent 隔离后的结果，而不是只报告当前三个非盲样本；
- 普通非空状态确实能通过 production action catalog 选择并 replay SAM3 box。

在这些证据形成前，不冻结“SAM3 优先”或“仍只允许 empty scan 使用 box”的新策略。

## 问题二：Verifier 候选复核是否对任何副作用过于严格

### 当前正式 staged 路径是谁在决定

当前正式 v12.1 staged 路径分三层：

1. **Qwen Model Verifier**：对 candidate delta 的局部 RGB/mask 面板输出结构化 JSON，主要是
   `region_id、t1_state、t2_state、evidence_quality`。模型不直接输出最终 `accept/comparison`。
2. **Python semantic policy**：
   `change_agent/adapters/staged_verifier.py:1121-1229` 根据动作方向和视觉判断派生
   `intended_error_improved、introduced_false_positive、introduced_false_negative、boundary_or_artifact_worsened`。
3. **Environment commit/rollback**：`change_agent/environment.py:422-452,572-630` 只有在候选被判为
   `comparison=better` 且 `accept=true` 时提交，否则保留审计记录并恢复 previous accepted state。

因此“Verifier 输出 JSON，程序做最终 commit/rollback”本身是为了让策略可审计、可复现，并不是问题的根源；
需要审查的是 Python 中冻结的决策语义是否合理。

### 必须纠正的表述

线上 Verifier 不读取 GT。当前代码中的“真实变化”实际是：Qwen 根据局部 RGB 把某个 delta region 判断为
`t1_state != t2_state`。当该 region 被候选删除时，程序把它派生为 `introduced_false_negative=true`。

这有两种对称风险：

- Qwen 把很小的被删区域误判为真实变化，可能 false reject 一个净收益很大的候选；
- Qwen 把真实变化误判为两时相相同，程序也可能 false accept 一个有害候选。

不能把它写成“程序知道删除了 GT 像素”，也不能把离线 GT metric gate 与线上 Qwen semantic review 混为一层。

### 为什么它在结构上偏严格

`change_agent/verifier_protocol.py:476-494` 当前规则是：

- intended improvement 且没有任何 harm → `better`；
- 只有 harm → `worse`；
- improvement 与 harm 同时存在 → `uncertain`；
- 视觉证据不足、mixed 或不一致 → `uncertain`。

Environment 只接受 `better`，所以当前语义是 magnitude-blind 的 zero-new-harm/Pareto policy：大幅纠正错误、
同时损失少量区域，也会整体回滚。`selection_epsilon` 不会改变已经有离散 `comparison` 的 staged 输出，
`verifier_accept_threshold` 也没有传给正式 staged verifier；这一语义目前不是配置项。

但目前只能说它**结构上可能对净 IoU/F1 目标过于保守**，不能说已经实验证明它过严：

- 0804 GT-direct teacher 的 Qwen 调用为 0，没有测试 staged Verifier；
- 0802 冻结 H0/H1 core3 只审到 3 个 Qwen reject，离线 GT 都判为 harmful，`qwen_false_reject_count=0`；
- 样本过少，既不能证明策略足够安全，也不能证明存在高 false-reject 率。

此外还要单列 pre-Qwen hard gates：mask area delta、ROI 外变化、target mask change、component count 与 point
combined gate。它们可配置，并可能在 Qwen 前直接拒绝候选；它们不是本节的 zero-harm semantic policy。

### 需要开展的 GT-blind-first 离线复核

在改策略前，应复用既有候选 artifact 做 replay/calibration：

1. 先冻结 Verifier 可见输入并运行全部 Qwen/程序判断，再打开离线 GT，防止 label 泄漏。
2. 对每个候选记录：
   - hard-gate 与 semantic-gate 的完整拒绝原因；
   - `ΔTP、ΔFP、ΔFN、ΔIoU、ΔF1、pixel-error reduction`；
   - 变动区域大小、是否跨对象、是否存在 mixed delta；
   - 当前 Verifier 的 `better/worse/uncertain` 与最终 accept/rollback。
3. 形成 true accept、true reject、false accept、false reject 四象限，并报告：
   - beneficial false-reject rate；
   - harmful false-accept rate；
   - rollback regret；
   - catastrophic harm rate；
   - 按工具、动作类型、区域大小与 error type 的分层结果。
4. 至少比较：
   - P0：当前 zero-harm policy；
   - P1：有明确 improvement margin 与 harm cap 的 bounded-tradeoff policy；
   - 必要时 P2：先 rank 多个候选，再让 semantic gate 对 top-1 做 fail-closed 复核。

P1 的 margin、harm cap 和容忍单位必须由离线 calibration 与 held-out validation 决定，不能凭感觉直接放宽。
schema invalid、证据不足、越界/非局部改动和灾难性删除仍应 fail closed；需要软化的是“任何微小语义副作用都等同
整条候选失败”的量级无关规则，而不是删除全部安全边界。

### Verifier 复核放行门

- 明确区分 hard gate、semantic gate 和 offline metric gate；
- 在 parent-disjoint validation 上同时约束 beneficial false reject 与 harmful false accept；
- 新策略对 SAM3 box 与 SimpleClick point 都有分层结果，不能只优化一种工具；
- 所有在线输入保持 GT-free；
- 阈值、tradeoff 公式、失败处理和 rollback 语义在实验前预注册；
- 新策略未通过前，不修改正式 gate，也不重解释 0803/0804 结果。

## 问题三：`max_steps=3` 不是经过标定的停止策略

### 已确认事实

- `ChangeAgentEnvironment` 的通用默认值是 8：`change_agent/environment.py:40`；
- `configs/default.json` 也是 8，但当前 CPU/GPU 运行配置、P1 H0/H1 freeze、0803 oracle 和 0804 GT-direct
  teacher 都将正式预算冻结为 3；
- 0804 teacher runner/validator 还把 3 写成正式合同，不能在旧 attempt 内临时改变；
- 因此 3 是当前实验预算和结论边界，不是已经证明的最优步数。

0804 的证据需要按失败类型解释：

- `train_407`、`train_364` 的 safe/raw 轨迹均连续改善三步后因 `max_steps` 停止，支持独立测试更长 horizon；
- `val_43` 的 safe 轨迹首步就没有可接受动作，单纯增加 safe `max_steps` 无法解决 gate 问题；
- `val_43 wide_raw` 连续改善三步，只能支持在绕过 gate 的 teacher 上限分支继续检查，不代表线上安全轨迹可继续。

### SegAgent/SimpleClick 可复用什么

当前冻结的 SegAgent 外部源码为
`/guisongxia01/pangchao/wangyihan/Chang-Agent/third_party/SegAgent`，commit
`21eca0a76a800440f3e4d8a8300b65f59f8dc782`。其 bundled SimpleClick trace 代码
`third_party/SimpleClick/isegm/inference/evaluation.py:57-161` 使用三类停止条件：

1. 达到 target IoU；
2. 当前 IoU 不再严格增加；
3. 达到最大 click 数。

对应评测脚本默认 `target_iou=0.98、max_clicks=20`，但这些数值来自通用单对象交互分割评测，不等于
SegAgent 论文正式训练数据一定使用的冻结数值，也不适合直接复制到 LEVIR-CD change detection。可复用的是
“目标阈值 + 边际收益/停滞 + hard cap”的结构，而不是照抄 `0.98/20`。

### 建议的新 adaptive-horizon teacher 实验

这是未来实验草案，今日不提交：

1. 先以 `train_364_r0c2` 做非盲 diagnostic smoke：它三步后 `FP=213`、目标 `FP<=64`，四条 track 都连续
   改善，最适合检查第 4 步以后是否继续收敛。
2. smoke 只能帮助调试停止逻辑，不能单独决定正式 `max_steps`；随后必须加入非空 GT、parent-disjoint 的小型
   train/val 样本。
3. 为避免空 GT 与非空 GT 使用完全不同的“变化率”，建议同时记录统一 pixel error：

   ```text
   E_t = FP_t + FN_t
   relative_gain_t = (E_{t-1} - E_t) / max(E_{t-1}, 1)
   ```

   仍单独报告 IoU/F1；空 GT 使用残余 FP endpoint。
4. 每条 teacher trajectory 至少有四类停止条件：
   - 达到预注册 endpoint；
   - 没有 eligible beneficial action；
   - `relative_gain_t < tau_gain` 连续 `patience` 步；
   - 达到 `T_max` hard cap，或检测到重复 state/action/循环。
5. `tau_gain、patience、T_max` 只能通过 development set 的 step-to-endpoint 与 marginal-gain 曲线选择，并在
   held-out validation 上固定验证；不能在看到某个正式样本结果后继续加步。
6. 为控制 0804 式候选爆炸，上限诊断可先跑 raw-only、缓存相同 `state hash + action geometry + tool`，并复用
   embedding/model session；若要研究安全轨迹，再单独补 safe track。

必须区分两套停止策略：

- **离线 teacher/data construction**：GT 可用于 endpoint、benefit 和 `tau_gain`；
- **线上 production inference**：没有 GT，只能依据 Verifier 收敛、无可执行动作、重复/停滞代理信号和 hard cap。

离线找到需要 5、8 或更多步，不等于线上可以直接使用相同步数与停止判定；二者要分别预注册和验证。

### 停止策略放行门

- 报告 steps-to-endpoint 分布，而不是只给一个平均值；
- 按 `endpoint/no_beneficial/stagnation/max_steps/gate_blocked` 拆分终止原因；
- 给出每步边际收益、累计收益、工具类型、gate 与计算成本；
- 新 `T_max` 能覆盖大多数可达轨迹，同时有明确的收益递减和资源依据；
- production 停止规则保持 GT-free；
- 新实验使用独立 preregistration、freeze 和 append-only attempt，不改写 0804 attempt-0001。

## 问题四：`mixed_error` 被识别后没有原生可执行动作

### 已确认的实现事实

1. `change_agent/verifier_protocol.py:345-368` 会从 audit checklist 程序化派生错误类型：当至少一个
   false-positive 类检查与至少一个 false-negative 类检查同时失败时，结果为 `mixed_error`。它表示系统识别到
   同一区域同时存在“多出来”和“缺失/不完整”两类问题，不等于 `none`，也不等于证据不足的
   `uncertain_region`。如果 evidence 不足或任一 checklist 项为 uncertain，则程序会优先派生
   `uncertain_region`，即使其他检查已有明确 fail，也不会归为 `mixed_error`。
2. `change_agent/adapters/staged_verifier.py:1231-1282` 会把 `mixed_error` 纳入待处理 diagnosis 并赋予优先级，
   但 `:1284-1297` 的 `_plan()` 只接受 `false_positive_change` 与 `false_negative`，遇到 `mixed_error` 直接
   返回 `None`。因此 diagnosis schema 接受它，executor planner 却没有对应 action contract。
3. `_select_action_plan()` 会继续寻找同一轮中的其他纯 FP/FN diagnosis；若存在其他可执行区域，系统仍可先处理
   那些区域。真正的死路是：当前未解决区域只有 `mixed_error/uncertain_region`，或所有纯错误 diagnosis 也因
   target view/seed 不可编辑而无法形成 plan。
4. 在尚未到达 step budget 边界时，legacy/H0 的 `suggested_action=None` 会让 runner 以
   `verifier_no_executable_action` 停止；启用 H1 terminal review 时可以再做一次独立复审，但只有复审把问题改判为
   唯一可执行的纯 FP/FN 才能继续，持续为 `mixed_error` 时仍会落到
   `no_executable_action_after_review`。二者最终都归入 `episode_outcome=no_executable_action`
   （`tools/run_levir_change_agent.py:590-592,932-963,1597-1617`）。
5. 有一个必须单列的统计例外：若 H0/legacy 在最后一个允许动作后的 full re-audit 才得到 plan-null，Environment
   可能先因 budget 用尽置为 done，最终 stop reason 仍显示 `max_steps_reached`。因此后续统计必须联合读取每步
   `stage_trace diagnosis/plan`，不能仅凭 episode stop reason 判断是 horizon 耗尽还是 `mixed_error` 无动作。
6. plan-null 输出仍可能是 `verifier_valid=true、stop=false`，但 `suggested_action/error_region=None`；top-level
   `target_view` 还可能使用兼容性 fallback，不能把它当成真实 mixed repair target。审计应以 stage trace 中的
   diagnosis、plan 和 regional validation errors 为准。
7. 这条路径发生在 SAM3/SimpleClick 执行之前，也没有产生待 Verifier 复核的 candidate。因此不能把这种停止解释为
   “工具尝试后无改善”“候选被 rollback”或“`max_steps` 不够”。

### 为什么这是独立的系统缺口

对 `mixed_error` 直接不动作是一个安全的 fail-closed 默认值，因为单个 point/box 可能只修复一种极性、同时放大
另一种错误；但当前实现把下列情况合并成同一个空 plan：

- 一个对象区域确实同时有过分割与欠分割；
- proposal/audit region 过粗，把两个本可分别修复的子区域合并；
- Qwen 的 checklist 判断内部不一致；
- 确实不存在满足当前 geometry/seed 约束的安全单步动作。

这会造成“已经发现错误，但系统没有任何修复尝试”的 actionability gap，并可能让轨迹在第一步就停止。它与问题一
相关，但不等价：问题一是普通 region 的 point/box 工具选择被硬编码；本问题是连一个可供工具路由比较的单步修复
目标都没有形成。

### 候选设计方向（尚未冻结）

1. 不应把所有 `mixed_error` 机械映射成某个固定工具；先增加 refinement/decomposition，把它拆成带明确
   `error polarity + target_view` 的可审计子目标。
2. 保持 Environment 拥有 geometry 的边界：Qwen 只选择既有子区域和修复目标，不能凭自由文本创造 point/box；
   Environment 再为该子目标生成受约束的 SAM3 box 与 SimpleClick point 候选。
3. 每一步仍只执行一个动作。先选择净收益/风险最合适的一个子目标，执行并复核后重新审计 accepted state，再决定
   是否处理另一极性；不要在一个 JSON 中同时下发两个不可独立 rollback 的动作。
4. 若 refinement 后仍无法形成动作，应输出独立、可统计的 `mixed_unresolved/no_safe_subaction` 类终止原因，而不是
   与一般 parser/geometry 失败共用模糊的 `no_executable_action`，更不能把它当成 finish/converged。
5. 离线 teacher 可以对拆出的各极性候选做真实工具执行，用 GT 标注单步净收益、长期 endpoint value 和 selection
   regret；线上 decomposition/router 输入仍必须 GT-free。

### `mixed_error` 可行动性验证门

- 构造并覆盖纯 FP、纯 FN、同一区域 mixed、两个独立异极性区域、证据不足、parse/repair fail 和不可编辑 seed；
- 对初始 plan-null、`step < max_steps` 与 `step = max_steps` 后才出现 plan-null 分别做 H0/H1 同源 A/B；
- 报告 `mixed_error` 发生率、成功拆解率、产生合法动作率、beneficial/harmful action 比例和 no-action regret；
- 同时统计 `plan_null_reason`、最终 diagnosis、regional validation errors，以及合法 plan-null 被计入通用
  action-attempt error 的数量；
- 与当前 abstain baseline 配对比较 endpoint reachability、错误像素、IoU/F1、工具调用与有害动作率；
- 验证每个子动作都绑定 live region、明确极性与 target view，并能单独 replay/rollback；
- 对 repeated mixed diagnosis 设置循环检测与 hard cap，避免两种极性之间来回振荡；
- 在新协议通过前，不把 `mixed_error` 自动改写为 point/box，也不把当前 no-action 样本计作工具能力失败。

## 问题五：teacher-only 三步上限搜索的单样本吞吐不可接受

### 必须先正确解释“四小时三步”

0804 的 `max_steps=3` 是**每条 track 最多选择三个状态转移**，不是每个样本只调用三次工具。每个样本独立运行
`matched_safe、wide_safe、wide_hard、wide_raw` 四条 counterfactual track；每一步先对全部候选调用真实工具，
离线 GT 评分后才选一个 winner，并对 winner 再做一次 canonical replay。

| 样本 | 逻辑候选 | selected/replay | 约计物理编辑调用 | fresh 初始化 | 单卡耗时 | 混合平均耗时 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `train_407_r3c2` | 588 | 12/12 | 600 | 4 | `04:01:17` | `24.1 s/编辑调用` |
| `train_364_r0c2` | 672 | 12/12 | 684 | 4 | `04:44:52` | `25.0 s/编辑调用` |
| `val_43_r1c1` | 516 | 6/6 | 522 | 4 | `03:31:34` | `24.3 s/编辑调用` |
| 合计 | 1776 | 30/30 | 1806 | 12 | `12:17:43` GPU 时间 | `24.5 s/编辑调用` |

“混合平均耗时”由 shard 总耗时除以候选执行与 replay 次数得到，包含模型启动/加载、预处理、推理、Environment、
artifact 写入与哈希等开销，不能写成 SAM3 或 SimpleClick 的纯模型延迟。1806 只计编辑调用；每条 track 另有一次
fresh 双时相 SAM3 初始化，所以若统计全部 backend subprocess，三个样本分别为 `604/688/526`，合计 1818。

这不证明正常 production Agent 三步也要四小时：线上每步只执行最终选中的动作，不运行 0804 的 GT 穷举，且本轮
`qwen_invoked=false`。但对 teacher 能力边界、paired tool calibration 和未来轨迹构造而言，单样本 3.5–4.75 小时
仍然不可接受；若直接把 horizon 从 3 增到 5/8，成本还会继续放大，后续实验无法扩展到有统计意义的样本量。

### 已确认的直接成本来源

1. `tools/run_qwen3vl_gt_direct_teacher.py:1005-1133` 在每个 track、每一步用 Python 循环串行执行全部候选；wide
   geometry 每步最多 96 个候选，四条 track 的单样本三步理论上限为
   `3 × (4 + 3 × 96) = 876` 次候选执行。
2. 每个候选都会创建独立 branch Environment。`change_agent/adapters/subprocess_adapters.py:132-185` 为每次调用写
   image/mask，随后执行一次新的 `subprocess.run`；没有常驻工具进程。
3. 新 worker 会在每次 SimpleClick point 调用中重新 `load_is_model`，在每次 SAM3 box 调用中重新
   `build_sam3_image_model`（`tools/segmentation_worker.py:17-76,118-132`）。因此当前候选之间不复用 checkpoint、
   model session 或 image embedding。
4. 已有 worker report 提供了粗粒度实测：三个完整 shard 的 worker `elapsed_seconds` 分别合计约
   `10550.6/12070.5/9119.0` 秒，对应作业总耗时 `14477/17092/12694` 秒，合计约占 71.7%。这确认 worker 路径是
   主要成本，但该字段仍混合了每次 model load、预处理、forward 和 worker 内写盘；persistent canonical Environment
   只持久化状态，不持久化模型进程，每次 selected replay 仍会新建 subprocess 并重新加载模型。剩余约 28.3%
   也混合父进程、wrapper 启动、Environment、artifact 与哈希，不能在新增 phase profile 前进一步武断归因。
5. 四条 track 独立运行，尚未按 `source state + action + tool contract` 做跨 track 去重。前两个完整样本的三条
   wide track 最终轨迹相同，但相同分叉前的候选仍被重复真实执行。
6. 每个候选保留独立 PNG/NPY/report、mask state 和哈希，审计证据充分但存在重复编码与写盘开销；目前没有分阶段
   profile，不能先验断言模型加载、推理、写盘各自占比。
7. 30 次 canonical replay 只占约 `30/1806 = 1.66%` 的编辑调用，而且提供了三 mask hash 一致性证据。删除 replay
   节省有限并削弱 lineage，不应作为首要优化。

### 降本分层：先做科学协议等价优化

以下方向不应混在同一个实验结论中：

**A. 目标是保持逻辑候选与科学问题不变：**

1. 先增加分阶段 profile，至少拆出 worker 启动、模型加载、embedding/预处理、模型 forward、mask composition、
   gate/GT metric、artifact 写入、哈希与 replay 时间。
2. 建立 content-addressed deterministic cache。cache key 至少绑定 image/source-state hashes、完整 action geometry、
   click history、query、tool/model/config/worker commit；命中时复用原始 output mask 与 receipt，gate 和 GT score 仍按
   各 track 协议计算。选中动作继续做 fresh canonical replay。
3. 将 SAM3 与 SimpleClick 改为各自常驻的隔离 worker，在同一 GPU 上只加载一次模型；按 image hash 复用
   embedding，并支持同图 SAM3 multi-box、SimpleClick multi-point batch。SimpleClick batch 还必须绑定相同的
   initial mask、ROI 与 click-history context；隔离环境和凭据边界不能因常驻化而放松。
4. 逻辑候选仍逐个保留 ID、输出 mask hash、gate 与 metric；物理执行可以 cache/batch。批处理顺序或数值路径若使
   任一候选 mask hash 漂移，就不能直接宣称与 0804 科学等价。
5. 对重复 image/mask 输入使用内容寻址或硬链接，分别记录 artifact 编码/写盘耗时；不能为了提速删除复现所需的
   receipt、selected state 或 canonical replay。
6. 用 `sacct MaxRSS` 与 GPU 峰值显存重新标定 shard 资源。合理降低过量申请可提高 array 并发、缩短墙钟，但它不
   会降低总 GPU-seconds，必须与算法/执行层降本分别报告。

**B. 会改变搜索覆盖或科学问题，必须独立预注册：**

1. 只回答 gate-free 工具上限时运行 `wide_raw`。0804 三个样本对应 628 个 logical candidates 和 9 次 replay，
   约为原 logical candidates 的 35%；它不能再回答 hard/RGB gate 的反事实影响，而且仅做 raw-only 仍有数百次调用。
2. 先用不执行真实工具的 GT-free ranker 将候选缩到 top-k，再执行工具；需要同时报告相对 full enumeration 的
   coverage、best-action recall 与 selection regret。
3. progressive widening、早停或按区域/工具自适应分配 candidate budget 也会改变 teacher 上限定义，不能用其结果
   回写或替代 0804 attempt-0001。

### 效率放行门

- 在优化前冻结 reference sample、逻辑候选、工具/模型/config hash、初态 mask hash 与分阶段 profiling schema；
- 同时记录 logical candidates、physical backend requests、实际模型 forward、cache hit/miss、batch size、worker/model
  load 次数与 embedding reuse 次数，禁止继续用一个“候选数”混合所有成本；
- 分工具报告 p50/p95 latency，并拆分 load/preprocess/forward/write；报告每样本墙钟、GPU-seconds、GPU 利用率、
  `ReqMem/MaxRSS`、峰值显存、artifact 数量/体积与写盘时间；
- cache/resident/batch 等价实验必须保持逐候选 output mask hash、metric、gate、selected action、终止原因与 final mask
  hashes 一致，canonical replay 三 mask 一致率为 100%，独立 validator 全通过；
- 若做 full four-track 等价复现，逻辑候选仍应为 1776、selected/replay 仍为 30/30；允许减少的是重复物理执行和
  model load，不是悄悄减少科学候选；
- 若先做 raw-only 低成本 pilot，应复现对应的 628 logical candidates、9 个 selected/replay、三条动作序列、逐步指标
  与 final mask hashes，并继续标记 `teacher_only=true、training_authorized=false`；
- 在正式实现前根据预计样本量与 horizon 预注册可接受的 per-sample SLA、总 GPU-hour budget 和最低 speedup；未达到
  SLA 时不启动大规模 paired routing、adaptive-horizon 或数据构造作业；
- 所有性能实验使用新的 append-only attempt，通过 Slurm 运行；不能覆盖 0804，也不能用缓存命中结果伪装成新的
  独立工具执行证据。

## 五个问题的依赖关系

五个问题不能完全独立处理，其中效率不是最后才处理的附属优化，而是其余验证能够扩展的基础设施门：

1. 先建立成本 profile，并验证 cache、常驻模型、embedding 复用和 batch 的等价执行路径；否则后续每个 paired
   ablation 与更长 horizon 都会重复支付当前候选穷举成本；
2. 再扩展普通 region 的 point/box 候选表面，并让 `mixed_error` 能拆成可审计的单步子目标；
3. 建立 GT-free tool/subaction router，决定同一状态下先修哪一种极性、使用哪个工具；
4. 对新增 SAM3 box 和 mixed sequential repair 重新标定 Verifier/hard gate；
5. 工具路由、mixed actionability、候选 gate 与效率 SLA 稳定后，最后才冻结 adaptive stop 与 `T_max`，区分
   horizon 不足、无可执行动作、动作选择错误和 rollback。

推荐的证据顺序为：

```text
成本 profile / logical-vs-physical 调用账
→ cache + resident model + batch 等价性门
→ 普通 region point/box 候选覆盖
→ mixed_error refinement / 单子目标 actionability
→ GT-free tool router / candidate ranker
→ hard 与 semantic gate calibration
→ adaptive teacher horizon
→ GT-free production stop policy
→ exact-commit Slurm 验收
→ 新版本 freeze
```

## 新版冻结、SFT 与能力边界的放行条件

解决本文件五个问题是新 freeze 的必要条件，但不是自动启动 SFT 的充分条件。新版本冻结前至少还应满足：

- action catalog、tool router、gate policy、stop policy 和预算均有机器可读 preregistration；
- `mixed_error` 有可审计的 decomposition/单步修复合同，或有独立且准确的 unresolved 终止语义；
- teacher/boundary runner 达到预注册的 per-sample SLA，且 cache/batch/resident worker 通过逐候选等价性验证；
- GT-free production 候选能覆盖 teacher 有效动作，并报告 improvement regret；
- 真实工具 replay、连续状态和 best-state/rollback lineage 可复现；
- 代码、配置、数据/模型/tool hash 与 exact commit 通过 Slurm 全量验收；
- deployable trajectory 能到 endpoint，并能从同源轨迹生成无 GT 泄漏的正式 T-TRAJ/C-ISO；
- parent/location train/val/test 隔离、schema、lineage、hash 与训练授权均通过。

之后才能考虑两条隔离、可并行的工作流：

1. **SFT 线**：只使用通过 deployable trajectory/data gate 的正式数据，保留 base 对照、token/step 匹配和
   独立评测；
2. **能力边界线**：继续用 teacher-only GT oracle 研究更宽工具、geometry 与 horizon，但其 artifact 始终标记
   `training_authorized=false`，不能自动流入 SFT。

两条线必须使用独立分支/worktree、输出目录、manifest 和 receipt，避免 teacher-only 数据污染线上训练结论。
